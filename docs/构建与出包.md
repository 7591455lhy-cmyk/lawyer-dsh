# 构建与出包

从源码到 `摸鱼工作站-Setup-<版本>.exe`。命令都在 Windows PowerShell 5.1 下验证过。

## 零、前置

| 依赖 | 要求 | 说明 |
| --- | --- | --- |
| 目录布局 | `deepseek-harness` 与 `lawyer-dsh` **并排**放在同一父目录 | 提供 esbuild 工具链与 dsh 源码；布局特殊时给 `build.ps1` 传 `-Harness <路径>` |
| Node | 22.19+ 或 24+ | 构建与运行 |
| pnpm | 11.7.0 | 装配 web profile（`nodeLinker: hoisted`） |
| npm | 随 Node | 安装 dsh 与 electron-builder 依赖 |
| dsh-worktable | 已装进本机 web profile | `prepare-runtime.ps1` 会检查 `%USERPROFILE%\.dsh\profiles\web\node_modules\dsh-worktable\lib\client.js` |
| claude-for-legal-ZH | 与 lawyer-dsh 并排（或 `-LegalZhDir` 指定） | 中国法语料与 18 个 dsh adapter；缺失时脚本直接失败 |
| 网络 | 需要 | 下载 Node 发行包、npm 安装 dsh、pnpm 装 profile 依赖 |

## 一、构建三个插件

```powershell
cd <lawyer-dsh>
powershell -ExecutionPolicy Bypass -File plugins\lawyer-sidebar\build.ps1
powershell -ExecutionPolicy Bypass -File plugins\lawyer-tools\build.ps1
powershell -ExecutionPolicy Bypass -File plugins\lawyer-wizard\build.ps1
```

> **M8.12 起演示数据已从源码删除**：原 `demo-artifacts/`、`demoData.ts`、
> `demoArtifacts.data.ts` 与 `-NoDemo` / `__LAWYER_DEMO__` 编译开关一并移除，
> 三个表单不再有「⚡ 载入演示数据」按钮与演示回放链路，构建产物也不再区分
> 「带演示 / 无演示」两种形态（`client.js` 约 360KB）。出包前无需再加 `-NoDemo`。

构建产物自检：

```powershell
node plugins\lawyer-sidebar\.check-portal.mjs
```

## 二、组装 runtime

```powershell
cd packaging
npm install
npm run prepare-runtime
# 带自己的工作台项目数据（一级子目录 = 一个项目）：
npm run prepare-runtime -- -WorktableDataDir D:\你的项目数据
```

产物 `packaging/runtime/`（约 310MB）：

| 目录 | 内容 |
| --- | --- |
| `node/` | 官方 Node win-x64（与 Electron 内置 Node 解耦） |
| `dsh/` | npm 安装的 `@deepseek-ai/dsh`（自包含依赖树） |
| `plugins/` | 三个插件 + `dsh-worktable` 的构建产物 |
| `profile-web/` | 预组装 web profile（pnpm hoisted，`file:` 依赖已复制） |
| `agent-presets/lawyer/` | lawyer agent preset |
| `skills/` | 律师技能 |
| `legal-zh/` | 中国法语料 + 18 个 adapter（上游 `LICENSE` 一并保留） |
| `worktable-data/` + `worktable-projects.json` | 工作台项目数据与清单 |
| `VERSION` | 部署版本标记（取自 lawyer-sidebar 的 version） |

`VERSION` 是「用户机器上要不要重新部署 profile / preset」的唯一判据，**版本
升级必须让它变化**。

未指定 `-WorktableDataDir` 时（仓库内不含项目数据），脚本会生成占位项目
`示例项目`，保证安装包可启动——`electron/main.js` 的 `assertRuntime` 要求
`worktable-data` 与 `worktable-projects.json` 必须存在。

脚本自带两处依赖树完整性校验（dsh 与 profile-web）：任何「有目录却缺
`package.json`」的包都视为 npm 安装中断的残留，会强制重装。

## 三、出安装包

```powershell
cd packaging
powershell -ExecutionPolicy Bypass -File scripts\_clean-dist.ps1   # 必做，见坑 3
npm run dist
```

产物：`packaging\dist\摸鱼工作站-Setup-<版本>.exe`（约 175MB）。

出包后自检：

```powershell
node .check-pkg.mjs
```

它会校验：exe 存在、打包进安装包的 `client.js` 无演示数据残留、三个里程碑
的功能锚点（三入口 / 中国法 adapter / MCP 工具名 / 画像 / 引导 / 完整问卷
分支 / 按钮配色修复）都在、`runtime/VERSION` 与三个插件版本一致、legal-zh
adapter 数为 18。

## 四、macOS 出包（dmg）

Apple Silicon 与 Intel **各出一份**（原生依赖与随包 Node 都按架构分开装）：
`packaging/dist/MoyuWorkbench-<版本>-arm64.dmg`、`...-x64.dmg`。

### CI 出包（推荐）

推 tag 或手动触发 `build-mac` 工作流（Actions → build-mac → Run workflow）。
它按 matrix 跑 arm64 / x64 两个 job：克隆中国法语料 → `prepare-runtime.mjs` 组装
runtime → `sips`/`iconutil` 生成 icns → `electron-builder --mac dmg --<arch>` →
`.check-mac-pkg.mjs` 自检 → 用包内 Node 起 `dsh web` 冒烟 → 上传 artifact（tag 触发时
还上传 Release）。

```bash
git tag -a app-mac-v0.81 -m "摸鱼工作站 0.81（macOS）"
git push origin app-mac-v0.81
```

### 本地 Mac 出包

```bash
brew install node@24
corepack enable && corepack prepare pnpm@11.7.0 --activate
git clone --depth 1 https://github.com/CSlawyer1985/claude-for-legal-ZH.git ../claude-for-legal-ZH

cd packaging
npm install
node scripts/prepare-runtime.mjs --platform darwin --arch arm64   # Intel 机器用 --arch x64

# 图标（缺了会用 Electron 默认图标）
mkdir -p build/icon.iconset
for s in 16 32 128 256 512; do
  sips -z $s $s build/icon.png --out "build/icon.iconset/icon_${s}x${s}.png" > /dev/null
  d=$((s * 2)); sips -z $d $d build/icon.png --out "build/icon.iconset/icon_${s}x${s}@2x.png" > /dev/null
done
iconutil -c icns build/icon.iconset -o build/icon.icns && rm -rf build/icon.iconset

rm -rf dist                       # 必做，见坑 3
npx electron-builder --mac dmg --arm64
node .check-mac-pkg.mjs --arch arm64
```

### macOS 侧的四个坑

1. **出包前必须提交插件产物。** 插件 `lib/` 已入库，CI checkout 只拿已提交的版本；
   改了 `src/` 而没重建并提交，dmg 里就是旧产物（Windows 是手工出包，反而不容易忘）。
2. **交叉构建必须按目标架构装原生依赖。** 在 Apple Silicon 上打 x64 包时，
   `prepare-runtime.mjs` 给 npm 传了 `npm_config_arch` / `npm_config_platform`，
   否则 koffi 会装成 arm64，Intel Mac 上加载失败。
3. **随包 Node 的可执行位。** tar 解压通常会保留，但 `cpSync` 之后要复查
   （`.check-mac-pkg.mjs` 有断言）；丢了的表现是启动即失败、dsh 起不来。
4. **未签名必然触发 Gatekeeper。** 首次打开要 `xattr -cr` 或右键打开——这是既定
   状态，不是产物损坏（安装文档里已写明）。

## 五、三个必踩的坑

**坑 1：版本号必须是完整 semver。**
`"version": "0.80"` 会被 electron-builder 直接拒绝：

```
⨯ Invalid version: "0.80"   at fixVersionField (app-builder-lib/…/normalizePackageData.ts)
```

因此版本字段一律写 `0.80.0`；若想让文件名也保持「0.80」，把
`build.win.artifactName` 写成固定的 `摸鱼工作站-Setup-0.80.exe`（代价：升版
要改两处）。用 `${version}` 宏时文件名会是 `…-0.80.0.exe`。

**坑 2：`--define` 不等于死代码消除。**
esbuild 只把 `__LAWYER_DEMO__` 替换成字面量，却保留 `if (false) {...}` 的原文；
死分支里对已被 tree-shaking 掉的模块的引用就成了悬空标识符（`DEMO_ARTIFACTS`
等）。构建脚本里必须保留 `--minify-syntax`（只做语法级死代码消除，不改标识符、
不压空白）。

**坑 3：出包前必须清旧 dist。**
`win-unpacked` 有近万文件，electron-builder 删旧目录时会撞上环境的批量删除
保护（大量删除需确认），表现为打包卡住或失败。先跑
`scripts\_clean-dist.ps1` 再 `npm run dist`。

**坑 4：dsh 版本可能与 `runtime/dsh` 实际安装树脱节（已修）。**
旧守卫只看 `runtime/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js` 是否存在
（外加依赖树完整性校验），`$DshVersion` 根本不参与判断。于是「改了版本号但没
重装」会静默沿用旧树——实测出现过脚本声明 `0.1.5-alpha.2`、而 `runtime/dsh`
里实际是 `0.1.1-rc.2`，装出来的包与配置声称的版本不一致。
现已修：`prepare-runtime.ps1` 与 `prepare-runtime.mjs` 都会读已装
`@deepseek-ai/dsh/package.json` 的 `version` 与目标比对，不一致即删树重装，
**不需要再手工删目录**。若仍怀疑有残留，手工删掉 `runtime/dsh` 再跑本脚本即可。

**坑 5：宿主注入的 `NODE_OPTIONS` 会让 npm / pnpm 安装中途失败。**
本开发环境通过
`NODE_OPTIONS=--require=...CodeBuddy.../vendor/shim/node-language-shim.cjs`
注入了一个语言垫片（内含 safe-delete 保护）。该变量被**所有** node 子进程继承，
会干扰 npm / pnpm 的 store 操作，典型症状是安装**静默中断**（日志停在
`added N/1266` 且没有 `Done in`），并在 node_modules 里留下大面积依赖链接缺失
——后续表现为看似无关的两个故障：`tsdown` 报 `Cannot find package
'@jridgewell/sourcemap-codec'`（client bundle 生不出来）、`tsc -b` 报上千个
TS2339（全是测试文件里的 `expect(x).not` 之类，生产代码却零错误）。
`prepare-runtime` 内部的 `npm install @deepseek-ai/dsh` 同样会受影响。

出包 / 装依赖前先清掉：

```powershell
$env:NODE_OPTIONS=''
```

`debug-web.cmd` 与打包壳 `electron/main.js` 都已内置这一清除。若 store 已被
污染（报 `ERR_PNPM_READ_FROM_STORE` / `ERR_PNPM_ENOENT ... unlink`），再补一次
`pnpm store prune`；依赖树已损坏时 pnpm 不会自愈（`install --force`、删
`.modules.yaml` 都只回 "Already up to date"），必须删掉 `node_modules` 重新安装。

## 六、版本号同步规则

一次升版要改的地方（漏一处就会出现「界面显示的版本」与「实际重部署的版本」
不一致）：

| 位置 | 作用 |
| --- | --- |
| `packaging/package.json` → `version` | electron-builder 的版本（安装程序元数据） |
| `packaging/package.json` → `build.win.artifactName` | exe 文件名（若用了固定名） |
| `packaging/package.json` → `build.dmg.artifactName` | dmg 文件名（用 `${version}` 与 `${arch}` 宏，升版不用改） |
| `plugins/lawyer-sidebar/package.json` → `version` | **源头**：`runtime/VERSION` 由 `prepare-runtime.ps1` 从它派生 |
| `plugins/lawyer-tools` / `lawyer-wizard` → `version` | 保持一致，便于回溯 |
| `packaging/.check-pkg.mjs` | 版本一致性断言与 exe 名 |

顺序：**先改版本 → 重建插件 → 重跑 prepare-runtime → 再 dist**。
改了 `src/` 而没重建就出包，仓库里的 exe 与源码就不是同一份。
